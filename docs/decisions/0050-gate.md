# 0050 Gate: Token und Review-Unabhängigkeit auf dem Host

Status: angenommen

## Entscheidung

- Ein Linux-Benutzer `pipeline-gate` je Host hält Token und Review-Schlüssel aller Projekte ([`gate.py`](../../host/gate.py)). Der Benutzer des Autopiloten hat keinen Token; per sudoers darf er nur `/opt/pipeline/gate` als `pipeline-gate` aufrufen, das Gate wählt das Projekt nach `SUDO_UID`. Ein Gate je Projekt ist die Rückfallebene.
- `git` geht über den Transport `ext::` (`insteadOf` in `~/.gitconfig`): Das Gate gleicht einen Spiegel mit GitHub ab und bedient `upload-pack` und `receive-pack`; ein `pre-receive`-Hook lässt nur Fast-Forwards auf `issue-*` und `bump-pipeline-*` zu und pusht sie zuerst nach GitHub. So bleiben `git fetch`, `pull` und `push` in Skills und Skripten unverändert.
- `gh` geht über eine Allow-Liste des Gates (`~/.local/bin/gh`); der Token steht nur in der Umgebung des Gates, nie in Argumenten.
- `gate review` startet `claude -p` als `pipeline-gate`: neuer Prozess mit eigener Session-ID, nur Read, Grep und Glob, `--restricted` (keine Einstellungsdateien, also keine Hooks eines PRs als Gate; die Dateiwerkzeuge bleiben in den Exporten, da `pipeline-gate` Token und Bäume aller Projekte lesen kann), Arbeitsverzeichnis und `CLAUDE.md` vom Default-Branch, keine Checks (sie liefen Code des PRs mit Zugriff auf den Token). Das Ergebnis ist strukturiert; das Gate postet es mit Attestierung, legt Folge-Issues an und löst Threads auf. Eine Ausgabe mit Token oder Schlüssel irgendeines Projekts postet es nicht. Die Workflows mit `PIPELINE_REVIEW_KEY` checken die Basis aus, da sonst Code des Branches den Schlüssel ausgeben könnte. Das Gate führt `gh` nur mit bekannten Flags aus und verlangt den Wert eines kurzen Flags als eigenes Argument, sonst gingen `-F<Datei>` oder `-XPUT` an der Prüfung vorbei.
- `agent-review` und `gate merge` werten nur Attestierungen mit gültigem HMAC aus, nicht den Autor. Ohne Actions-Secret zählt `agent-review` vorerst den Text, damit ein Repository ohne Secret mergen kann; die Frage steht in einem Folge-Issue.
- `gate carry` überträgt ein attestiertes Approve ohne Review auf einen Merge-Commit, dessen erster Elternteil approved ist, dessen zweiter auf dem Default-Branch liegt, dessen Tree genau dem sauberen Merge (`git merge-tree`) entspricht und bei dem der Default-Branch keine Datei des PRs geändert hat. Damit kostet ein nachgezogener Default-Branch nur CI, und der Merge-Commit kann keine eigenen Änderungen tragen.

## Verworfen

- Zweiter GitHub-Account als Reviewer: Es gibt nur einen.
- Review als GitHub-Actions-Job (`github-actions[bot]`): braucht einen API-Key als Secret und API-Abrechnung.
- Credential-Helper, der dem Benutzer den Token gibt: Dann kann die Session ihn lesen.
- Zwei Tokens (lesen für die Session, schreiben für das Gate): ein Token weniger einzurichten; die Allow-Liste des Gates ist die Grenze.
